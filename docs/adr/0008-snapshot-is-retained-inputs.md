# A Snapshot is retained inputs, not an as-of timestamp plus fingerprint

The first design pinned a Snapshot as the as-of timestamp every query filtered on plus a per-table fingerprint, chosen over physical extracts for cost and to stay inside the warehouse's permission model. Independent review (finding 3) showed this detects drift but cannot reproduce history: late-arriving events with old timestamps, deletes and corrected rows change historical answers, whole-table fingerprints invalidate Analyses when unrelated rows arrive, and Postgres has no durable historical snapshot a later session can reach. We reversed it. A Snapshot is retained inputs: for v0 an immutable DuckDB fixture or bounded extracts with content hashes, recorded with SQL, parameters, definition versions, result hashes and engine version. Each Finding lists the guarantees it holds, which are not mutually exclusive: **artifact replay** (saved results and evidence render exactly as reviewed) and **analysis rerun** (saved SQL against the retained input version). **Refresh** is not a guarantee but an operation: newer data, always a new revision with an explanation of changes. Multi-table Postgres extracts are captured inside one `REPEATABLE READ` transaction so the retained inputs are one consistent view; content hashes alone do not establish cross-table consistency. Where inputs are not retained the Finding says "not reproducible" rather than implying otherwise. Fingerprints survive only as a drift signal over a declared dependency scope.
