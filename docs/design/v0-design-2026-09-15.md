# aftergrid v0 — settled design (2026-09-15)

Output of a `/grill-with-docs` session over `docs/inputs/data-agent-skills-handoff.md`, `docs/inputs/ramp.jpg` and `docs/inputs/research-notes-2026-09-15.md`. Vocabulary in `CONTEXT.md`; reasoning in `docs/adr/`. This file is the decision list; it is not a spec.

## Positioning
- **Finding-first.** The product is the Finding a non-data Reader trusts; skills, Checks, adapters and the Instance serve it. (ADR 0001)
- **Personas:** Operator (data-savvy, installs/maintains/reviews, works in Claude Code or Codex) and Reader (understands, inspects and follows up on Findings without SQL or a GitHub account).
- **Success test, two tiers** (after review finding 5). *v0 milestone (smoke):* golden Questions green in CI; first Finding passes the Reader subagent under a "non-technical product owner" profile; one outside person explains the answer in their own words, names the denominator and a limitation, and picks an action. *External release gate:* formative study with ~5 non-data participants and 2–3 practitioners across a correct, an inconclusive and a controlled-misleading Finding (debriefed); an outside Operator connects a bounded dataset, corrects a definition and regenerates a Finding; look for a second voluntary use on a real decision.

## The Finding
- Reader affordances (review finding 1): per Claim, **understand** (who is counted, vs what, over when), **inspect** (expand calculation, exclusions, evidence), **continue** (one follow-up / record-decision action by Finding + Claim id, routed to the Operator in v0).
- Claim type required: descriptive / associational / causal. Inconclusive, insufficient-data and needs-reframing are valid Findings that pass the template. Primary comparison is pre-registered before cuts.
- Canonical: `memo.md` + one Vega-Lite `.vl.json` per chart, rendered to SVG/PNG, plus queries and Checks, reviewed as a PR in the Instance. (ADR 0003)
- Fixed sections, linter-enforced: Answer (one sentence) → Decision it informs → Evidence → How we checked (Checks, Snapshot) → What would change our mind → Appendix (queries). Evidence for an inconclusive / insufficient-data / needs-reframing Finding is the Claim stating why, with references to whatever partial results exist; the chart-or-table rule applies only to Claims that assert a number.
- Narrative: answer-first. Each Evidence subsection is one Claim: a sentence heading; for numeric Claims ≥1 chart or table whose title states the Claim. Linter enforces structure; a narrative reviewer subagent judges coherence and Reader-level language.
- Visual iteration: autonomous in background runs (render → view PNG → score against rubric → revise). Three passes is a maximum, not acceptance: a chart still failing the rubric after pass 3 is returned for Operator attention. Scoring is advisory and never substitutes for provenance or method gates. Operator picks among Variants when in the loop via `/revise-finding`; Variants share pinned evidence and analytical semantics.
- Visual rubric seeded from *Storytelling with Data* (Knaflic): declutter, one message per chart, title = the Claim, direct labels over legends, grey + one accent, colorblind-safe. Checkable as yes/no items against a PNG.
- Reader lens: `analytics/readers.md` in the Instance holds named Reader profiles; each Finding names its Reader; the Reader subagent in `/analysis-review` adopts that profile, generic fallback if none.
- `/revise-finding` changes presentation and narrative only. Any change to a number or query reopens `/analyze` against the same Snapshot. Interpretation changes (causal wording, hidden comparison, aggregation, axis truncation) invalidate review even with no digit changed; cosmetic edits still re-render and get a visual look.
- Evidence model (ADR 0004 amended; contracts agreed with CobaltSpring 2026-09-15):
  - `results/<result-id>.json` + `manifest.yaml` with `schema_version`, Finding id/revision, and stable ids for inputs, executions, result sets, definitions. An execution binds SQL content hash, parameters (incl. analytical timezone), input ids/hashes, definition versions/hashes, result id/hash. A filename never identifies an execution.
  - Results have unique stable row keys, column types, units, execution id. References resolve by row key, never index; missing/duplicate keys or columns are rejected. Decimal precision preserved; null/not-available distinct from zero; rounding + percentage formatting defined once, applied only at display, never before a derived calculation.
  - Reference grammar `{{ref:<result-id>.<row-key>.<column>}}` with a restricted id charset so separators are unambiguous; points to a result-set identity in the pinned manifest; no expression language in the token.
  - Derived values: prefer SQL. Renderer-side derivations use a small declared operation set with referenced operands, units, and defined zero-denominator/null behaviour; cycles and arbitrary formulas rejected. Targets, assumptions, external references have explicit source types. Metric kind (metric / diagnostic) is separate from lifecycle status (proposed / approved / deprecated).
  - Each Claim has id, type, evidence references, population, baseline, window, exclusions, limitations, in the manifest. A Claim with no numeric result is representable.
  - Enforcement boundary: every data-bearing displayed value resolves from these records. Dates, section numbers and labels have explicit handling; targets need typed sources. Lint checks syntax and reference/value integrity; method review judges "doubled", "caused". Review/approval evidence is stored against a content revision.
  - Vega-Lite: allowlist over nested/layered specs and encoding-level behaviour, not just a top-level `transform` ban. No analytical binning, time grouping, stack normalisation or other untracked calculation in the initial subset. Chart data bound through the renderer to saved results; no inline replacement data, no remote URLs.
  - Retained inputs stay in the private Instance; the Reader export is a separate projection.
- Trust is shown as separate facts: Checks passed, definitions approved, method reviewed, limitations, reviewer + date. Never one badge or a confidence %.
- Publication binding: the manifest carries a content digest over memo, charts, queries, results and policies; approval and review attestations (source, reviewer, date) bind to that digest; owner contact, export policy (allowed fields, recipient scope), coverage, generated-at and supersession are manifest fields. `check` verifies required Check/review evidence against current Finding content and definition approvals against their own pinned immutable definitions; changes invalidate the applicable attestations, not unrelated definition approvals. `render` for publication refuses without a bound, current attestation set; a draft preview is allowed, labelled draft, cannot claim reviewed status, and still uses the reader-safe projection. Hashes prove binding, not reviewer identity; the v0 trust source is a current, non-dismissed GitHub PR APPROVED review by an allowlisted human at the exact analyzed commit SHA, verified through the API against trusted Instance policy independent of agent-edited Finding fields. A distinct automation identity authors the PR, and the runner cannot impersonate the reviewer. Unreachable API means readiness unknown, draft only. The digest covers semantic manifest + memo/query/Check/chart-spec/result contents and renderer/house-style versions; exclude self-hash, attestations, generated outputs and volatile timestamps. Regenerate outputs from validated source before publication. `check` reports evidence validity and publication readiness separately and never mutates hashed content.
- Sharing (ADR 0006 amended): each Finding names recipient, granularity, embedded fields, delivery location; render exports only the reader-safe payload; links carry ids not values; render shows coverage, generated-at, version, owner, superseded-by.
- Reader delivery: `aftergrid render` → single self-contained HTML, derived, never authored. One Reader action per Finding, "question or flag this", carrying Finding + Claim ids only. v0 contact route: a `mailto:` to the Finding's owner (from the manifest) with ids prefilled; the Operator files the GitHub Issue. No Reader needs GitHub. Slack/Notion/PDF in `in-progress/`.

## Revisit (ADR 0009, added 2026-09-15)
- A merged Finding is a standing test of the decisions that cite it. `aftergrid revisit` (v0.1): refresh Snapshot as new retained inputs → rerun saved SQL under the declared window policy → evaluate each Claim's Recheck policy and the Question's falsifier → new revision reporting per Claim: holds / contradicted / insufficient data / not comparable, and listing the Decision records that rest on each. Operator reviews; the decision owner judges; never an automatic verdict.
- **v0 must carry the schema**: per-Claim Recheck policy (tagged: predicate + threshold/direction, comparison method or versioned method ref, evidence refs, tolerance units + baseline where applicable, minimum-data/coverage, window policy fixed-window vs advancing-window; or not-automatically-evaluable + reason); a machine-checkable `falsifier` on the Question (a Check file + expected outcome); Decision records carry the Claim ids they rest on and a structured `revisit_when` (schedule, falsifier reference, or both). Recheck results (holds / contradicted / insufficient data / not comparable) are distinct from engine Check failures. The Engine never infers "decision holds".
- Marketing line under test: "the analysis that re-checks itself." Replaces the week-long "can you refresh that?" project.

## Engine
- Name `aftergrid`; repo `patrickjmorris/aftergrid`; MIT with Matt Pocock's notice retained.
- Structure mirrors mattpocock-skills: buckets (promoted / misc / in-progress / deprecated), user- vs model-invoked split, router `/ask-aftergrid`, `/setup-aftergrid` with hard/soft dependency split, `.out-of-scope/`, `/skill` prose references, docs page per promoted skill, Claude plugin + skills.sh + `openai.yaml` per skill. Recorded as a `CLAUDE.md` rule, not an ADR.
- Depend on `mattpocock-skills` for model-invoked `grilling` and `writing-for-agents` (setup checks it is installed). Recommend `handoff`, `research`, `to-questionnaire` as install-alongside.
- **CLI in TypeScript**, npm `aftergrid`: `new finding` (an incomplete draft with fresh ids), `check` (artifact verification or retained-input SQL rerun with distinct readiness), `render` (Vega-Lite → SVG/PNG and Reader-safe HTML), `decide` (explicit owner Decision record) and `intake` (labelled-Issue runner). Users write SQL, markdown, JSON only. (ADR 0005)
- Safety in hooks, roles, adapter guards; never prose alone. Hard permissions, privacy boundaries and execution limits have no bridge. Only exploratory reads of non-sensitive unverified sources may use logged provisional access with human sign-off, and their results are never shared. (ADR 0006 amended)
- Retained-input rerun on Postgres: bounded extracts are restored into a disposable compatible Postgres (container) with recorded schema and runtime requirements, and the original SQL reruns there. If no compatible runtime exists, SQL rerun reports unavailable while saved-result artifact replay remains available. A run never falls back silently to the live source. Controlled provisioning (restore) is distinct from agent-issued analysis SQL and is not subject to the statement guard. Seam-2 test: mutate the live source after capture and rerun the Analysis entirely from retained inputs.
- Adapter capability semantics are bounded, never universal: "role can write" = a probe of the connected role's privileges; "unbounded scan" = no supported non-executing estimate under the configured cap and no documented fallback with enforceable resource limits; a row LIMIT is never a scan-budget check; cost estimate = non-executing planner estimate in backend units, with `unknown` allowed (Postgres `EXPLAIN` without `ANALYZE`); budgets = supported enforceable runtime limits; statement timeout is explicit, Postgres work_mem is per-operation tuning rather than a total memory cap, and hard memory bounds require an enforcing runtime. An unsupported required capability fails or takes an explicit safe fallback, never reports zero cost or a green capability. Units come from evidence/metric metadata, `unknown` allowed. Source permissions and adapter limits precede any real-data execution; the harness hook precedes unattended intake.
- Adapters: **DuckDB + Postgres** promoted in v0. Postgres/Supabase coverage is a v0 acceptance target until its actual contract and private-pilot evidence pass. PostHog managed warehouse speaks Postgres wire but its snapshot, catalog, guard and SQL capabilities are **unvalidated**; a capability matrix per backend precedes any coverage claim. HogQL, Snowflake, BigQuery scaffolded in `in-progress/`, promoted when a consumer proves each. Adapter PRs open from day one; skill PRs maintainer-only until first Spot Sports-proven promotion.
- Snapshot = retained inputs (ADR 0008): immutable DuckDB fixture or bounded extracts with content hashes. A Finding lists the guarantees it holds (artifact replay, analysis rerun; not mutually exclusive); refresh is an operation that always yields a new revision. Postgres multi-table extracts are captured inside one `REPEATABLE READ` transaction so the extract is one consistent view; content hashes alone don't establish cross-table consistency. Fingerprints only as drift signal over declared dependencies.
- Metric definition = markdown + frontmatter (id, version, kind `metric | diagnostic`, lifecycle `proposed | approved | deprecated`, grain, population, denominator, window, owner, approver, reviewed revision) + canonical SQL per dialect. Kind and lifecycle are separate axes. (ADR 0007 amended)
- Decision record separate from merge: owner, action or deliberate inaction, rationale, date, revisit condition, outcome. Corrections close via a new Finding revision and, when needed, a definition update + regression fixture.
- Golden Questions assert answer within tolerance + Metric definition id used + tables read. No full-trace matching.
- Eval/demo data: deterministic synthetic consumer-app events (PostHog-shaped: users, events, subscriptions) with planted effects, on DuckDB in CI. Generator lives in this repo. Failure fixtures required (review finding 5): duplicate joins, zero denominators, population mix shift, late-arriving events, missing instrumentation, wrong evidence references, insufficient data; expected outcomes include refusing an unsupported conclusion.
- Golden Question = reference case with expected answer *or expected abstention*, with tolerances.
- Intake: GitHub Issues with Matt's triage labels; `ready-for-agent` → background run → Finding PR linking the Issue. Cron, Slack, metric alerts in `in-progress/`.

## Assumptions made without asking (cheap to reverse)
- Finding directory in the Instance: `analytics/findings/<yyyy-mm-dd>-<slug>/{memo.md, manifest.yaml, queries/, checks/, charts/}`.
- Decision log is `analytics/decisions.md`. Entries are explicit Decision records written via `aftergrid decide`, a deterministic command with idempotent append and exact Finding/Claim references; neither merge nor `/revise-finding` creates a decision.
- Findings show separate facts in the render: Checks passed, definitions approved, method reviewed (reviewer + date), limitations, Snapshot guarantees. Approval is recorded against a content digest, not a frontmatter field. Freshness copy is accurate: a downloaded HTML can only state its generated-at and coverage and point at a canonical location for newer revisions; it cannot discover supersession by itself.
- v0 hooks target Claude Code (PreToolUse); adapter enforcement is portable, but harness safety claims require tests of supported alternate query/export paths.
- Chart house style is a shared Vega-Lite config; every chart title states the claim, not the axis.
- `/setup-aftergrid` scaffolds the Instance; no separate template repo.

## Owner-requested per-bead revision (2026-09-15)

The [plan-space review](bead-plan-review-2026-09-15.md) records the current execution order and acceptance contracts, synchronized with the spec. This preserves the chosen v0 feature scope.

- Reviewed numeric/nonnumeric synthetic exemplars, schema and a real Reader response precede implementation. A hand-authored private DuckDB Finding with Reader feedback precedes writer and question/analysis skills. Neither gate may be completed by a simulated Reader.
- `/grill-question` and `/analyze` share an internal clarification procedure rather than one user-invoked skill calling another. Avoid repeated questioning; unresolved Questions/needs-input and valid insufficient-evidence Findings do not fabricate executable falsifiers.
- `aftergrid decide` has its own deterministic task. Generator/reference Questions run early; nightly model evaluations are a separate later task.
- Renderer uses a WASM rasterizer for PNG previews and pinned style/runtime versions. Supported installs require no local compilation; prebuilt native runtimes are permitted. Mobile reading, keyboard expansion, chart descriptions/data tables and copyable contact fallback are part of the Reader contract.
- DuckDB reports Postgres-style role probing unsupported and uses a read-only local-file policy. Hook rules target protected source operations, not routine local artifact writes, and do not claim to be a universal shell sandbox. Verified scoped provisional status propagates to derived values and remains unshareable.
- Intake is a CLI poller with stable run/PR identity, needs-input resume, restart/concurrent-trigger tests, and hook/limit preflight. Actions integration remains optional.
- All v0 tasks lead through blocking dependencies to the internal milestone. Complete package smoke includes setup, hook, decide and intake. Public package/source activation and the agreed formative external-release validation are a separate follow-on; scheduling the study is not passing it.
